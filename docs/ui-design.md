# あっち向いてホイ — モバイル UI / UX 設計方針

## 1. この文書の目的

この文書は、`docs/ui-contract.md` を前提として「あっち向いてホイ」アプリのモバイル UI / UX を全面的に再設計するための設計方針をまとめる。

ここで定義するのは主に以下である。

- アプリ全体の画面構成
- 各画面の役割
- 対戦体験の基本構造
- 学習・検証・設定の位置づけ
- ナビゲーション方針
- 子どもでも迷わず遊べるための UX 原則
- ビジュアルデザインの方向性
- 実装時に守るべき UI の判断基準

一方で、ピクセル単位の余白、各ボタンの正確な位置、アニメーション時間、最終的な文言、細かなコンポーネント構成などは実装後の実機確認で調整する。

この文書は完成したデザインカンプではない。実装時の判断がぶれないための「UI 設計上の基準」とする。

---

## 2. 参照仕様と優先順位

UI は以下のドキュメントをバックエンド側の前提・制約として扱う。

1. `docs/ui-contract.md`
2. 必要な場合のみ `docs/backend-spec.md`

特に以下は UI 都合で変更しない。

- Pointer と Face は別分類である
- 対戦には Pointer / Face 双方の判定が必要
- じゃんけんは存在しない
- 対戦開始時に先攻 / 後攻を選択できる
- 1 点勝負 / 3 点先取を選択できる
- 1 ポイント中は決着まで攻守交代する
- 3 点先取ではポイントごとに開始攻守が入れ替わる
- 判定不能時には得点も攻守も変えず、同じ手を再試行する
- 対戦可能かどうかは UI がサンプル数から独自判定せず、バックエンドの `canPlay` 相当を信頼する
- Imported Dataset だけでも条件を満たせば対戦可能
- 共有データ ON/OFF はアプリ全体で 1 設定
- Local / Imported Dataset は別管理
- Export 対象は Local Dataset のみ

UI は KNN、MobileNet、Tensor、特徴量、類似度、IndexedDB 内部構造などを本番画面へ露出しない。

## 3. プロダクトとしての基本方針

### 3.1 主役は対戦

このアプリは「AI を学習させるアプリ」ではなく、スマートフォンで遊ぶ「あっち向いてホイ」のゲームとして見せる。

起動時の中心画面は対戦であり、学習・検証・設定はそのための補助機能として扱う。

ユーザーが通常利用時に最も長く見る画面は対戦画面である。

### 3.2 スマホ縦画面を主役にする

ゲーム部分はスマートフォンの縦画面を基準に設計する。

- 対戦は原則 1 画面完結
- 対戦中は縦スクロールしない
- 学習の撮影中も原則 1 画面完結
- 検証・設定は必要に応じて縦スクロール可
- ノッチ、ホームインジケータ、Android ナビゲーション領域などの safe area を考慮する

横画面向けに別の完成されたゲームレイアウトを設計する必要はない。対戦・学習中に横向きになった場合は状態を保持し、縦向きへの復帰を簡潔に案内する。

### 3.3 Web ページではなくスマホアプリとして見せる

実装は Web 技術でも、UI の基準は Web サイトではなくスマホゲームとする。

- Web サイト風の大きなヘッダーを置かない
- URL やブラウザ操作を UI の前提にしない
- 画面全体をゲーム領域として使う
- 将来的な PWA 化や Android アプリ化でも成立する構造にする

## 4. 想定ユーザーと UX の基準

主なプレイヤーとして、小学校 1 年生程度の子どもが自力で遊べることを重視する。

ただし「子ども向け教材」や「幼児向けアプリ」に見せることは目的ではない。

設計上の基準は次の通り。

> 子ども向け UI ではなく、子どもでも迷わないゲーム UI を作る。

そのため、対戦・学習では以下を重視する。

- 画面を読まなくても流れが分かる
- 1 つの瞬間に求める行動を 1 つに絞る
- 主要操作は大きく、誤操作しにくくする
- 長文説明を読ませない
- 短い言葉、キャラクターの動き、色・形の変化を組み合わせる
- 「失敗」「エラー」といった技術的・否定的な言葉をゲーム中に強く出さない
- 判定不能は「もういっかい！」程度の軽い再試行として扱う

対戦・学習の文言は、基本的に小学校低学年でも理解しやすい短い日本語を使用する。

例:

- `ゆびを さして！`
- `かおを むけて！`
- `あっちむいて…`
- `ほい！`
- `もういっかい！`
- `かった！`
- `まけた！`

検証・設定画面は大人が利用することを想定し、通常の漢字を含む日本語を使用してよい。

## 5. アプリ全体の画面構成

主要画面は以下の 4 つとする。

1. 対戦
2. 学習
3. 検証
4. 設定

### 5.1 対戦

アプリのホーム兼メインゲーム画面。

通常起動時はここへ入る。

### 5.2 学習

Pointer / Face の学習を行う独立画面。

ゲームを成立させるための準備ではあるが、データ管理画面には見せず、ゲーム世界のチュートリアルとして設計する。

### 5.3 検証

認識精度を確認するための独立画面。

子どもが通常遊ぶためには不要であり、大人が「正しく認識できているか」を確認するためのツールとして位置づける。

### 5.4 設定

共有データ、Import / Export、データ削除、完全初期化などの管理機能をまとめる。

---

## 6. ナビゲーション

4 画面を常時ボトムナビゲーションに並べない。

理由は、対戦・学習・検証・設定を同格に見せると、ゲームではなく「AI デモアプリ」「管理ツール」に見えやすいためである。

基本構造は以下とする。

```text
対戦（ホーム）
  └─ 右上メニュー
       ├─ 学習
       ├─ 検証
       └─ 設定
```

- 対戦画面を明確なホームとする
- 対戦画面右上に小さなメニューボタンを置く
- 学習 / 検証 / 設定はそこから遷移する
- 各サブ画面からは戻る操作で対戦へ戻れる

「おとなメニュー」のような別階層は追加しない。

検証は設定配下ではなく、独立した主要画面として扱う。

## 7. 対戦画面の設計

### 7.1 対戦画面はホームでありゲームステージでもある

対戦開始前と対戦中を別ページには分けない。

同じ対戦画面がゲーム状態に応じて変形する。

```text
対戦開始前
  ↓
ルール選択
  ↓
スタート
  ↓
同じ画面が対戦状態へ変化
  ↓
試合終了
  ↓
同じ画面で再戦 / 終了
```

画面遷移によって世界が切り替わるのではなく、1 枚のゲームステージが状態に応じて変わる感覚を目指す。

### 7.2 基本レイアウト

縦画面を大きく 3 層として考える。

```text
┌──────────────────┐
│ 上部: スコア / 試合情報 │
├──────────────────┤
│                  │
│ 中央: CPU キャラクター │
│       掛け声 / 演出     │
│                  │
├──────────────────┤
│ 下部: 自分のカメラ      │
│       必要な操作         │
└──────────────────┘
```

最も大きな視覚領域は中央の CPU キャラクターとする。

### 7.3 キャラクターを主役にする

対戦画面の視線の中心は CPU キャラクターであり、ユーザーのカメラ映像ではない。

カメラを 50:50 で並べる構成は避ける。ビデオ通話のように見えるためである。

### 7.4 カメラは補助表示

カメラ映像は、自分の姿や動きを確認するための小さな鏡として扱う。

- 常時大きく表示しない
- 対戦中の主役にはしない
- confidence や認識ラベルを常時重ねない
- 認識成立 / 不成立など、バックエンドから確実に取得できる状態だけ軽くフィードバックしてよい

UI はカメラ映像だけから独自に「近すぎる」「顔が切れている」「手が画面外」といった判定を行わない。

そのため、対戦中に以下のような状況依存ガイドを勝手に出してはいけない。

- `もうすこし はなれて`
- `手を画面に入れて`
- `顔を中央に`

これらを将来行う場合は、バックエンド側に明確な画角品質判定機能を追加し、UI 契約を更新してから行う。

### 7.5 今の番を「画面全体」で伝える

対戦中は、小さなステータス文字を読ませない。

フェーズごとに以下を組み合わせて、画面を見た瞬間に現在の行動が分かるようにする。

- 大きな短い言葉
- キャラクターのポーズ
- 色や背景の軽い変化
- 必要に応じたカメラ領域の強調

例:

#### プレイヤー攻撃

`ゆびを さして！`

#### プレイヤー守備

`かおを むけて！`

#### 掛け声

`あっちむいて…`

#### 判定タイミング

`ほい！`

### 7.6 対戦のテンポ

演出は派手さよりテンポを優先する。

- 「あっちむいて…」で短いため
- 「ほい！」で文字・キャラを一瞬強く動かす
- 判定結果は短く表示
- 得点時だけ少し大きめに反応
- 次の攻防へすぐ移る

毎回フルスクリーンの結果画面を挟み、ゲームを止める構成は避ける。

### 7.7 判定不能

判定不能は勝敗とは別物として扱う。

- 得点は変わらない
- 攻守は変わらない
- 同じ手を再試行する
- UI はゲームを終了させない

表示は `もういっかい！` 程度の軽いリアクションを基本とする。

### 7.8 勝敗

勝敗は明確に出すが、負けを過度にネガティブにしない。

- 勝ち: `かった！`
- 負け: `まけた！`
- CPU は敵役というより一緒に遊ぶライバル
- 煽りや過剰な落ち込み表現は避ける
- 勝敗後は自然に再戦へ進める

### 7.9 スコア

数字だけではなく、獲得した点を視覚的に理解できる表現を主役にする。

3 点先取なら 3 個のマーカーを双方に見せ、何点取ったか / あと何点かを一目で分かるようにする。

`2 - 1` のような数字表現は補助として使用してもよいが、主役にはしない。

### 7.10 対戦開始前のルール設定

開始前に以下を選択できる必要がある。

- あなたから / CPU から
- 1 点勝負 / 3 点先取

内部仕様の `player-first` / `cpu-first` や `targetScore` といった名称をそのままユーザーへ見せない。

具体的な選択 UI や設定保持方法は実装時に決める。

## 8. 初回起動

初回は `canPlay=false` になる可能性が高いため、通常の対戦ホームを見せて単純に「遊べません」とするのではなく、短いセットアップ導線を用意する。

大きな流れは以下。

```text
タイトル / 導入
  ↓
カメラ利用
  ↓
「まず うごきを おぼえさせよう」
  ↓
Pointer 学習
  ↓
Face 学習
  ↓
「じゅんびできた！」
  ↓
対戦ホーム
```

ここでは AI、モデル、学習サンプル、KNN などの技術説明は行わない。

子どもから見た意味は「ゲームに自分の動きを覚えさせる」で十分である。

2 回目以降は通常の対戦画面へ直接入る。

既存データが不足して `canPlay=false` になった場合は、対戦画面から学習へ自然に誘導する。

UI は不足件数から独自に `canPlay` を算出しない。

## 9. 学習画面

### 9.1 学習を管理作業に見せない

学習は「データを登録する作業」ではなく、ゲームキャラクターへ動きを教えるチュートリアルとして見せる。

対戦と同じキャラクター、色、ボタンの質感を使用し、別の技術ツールに見せない。

### 9.2 Pointer / Face の区別

内部では Pointer / Face と呼ぶが、子ども向け UI では理解しやすい言葉を使う。

例:

- Pointer → `ゆびのむき`
- Face → `かおのむき`

正式な最終文言は実装時に調整する。

### 9.3 初回はガイド付き、以降は個別補強可能

初回セットアップ時は、5 クラスを順に進められるガイド付きフローを基本とする。

その後は、学習画面から特定の方向だけ追加学習できるようにする。

つまり以下の二段構えとする。

- 初回: ガイド付き
- 2 回目以降: 必要な方向を自由に補強

### 9.4 1 回の学習体験

1 セッションは約 3 秒。

```text
対象方向を提示
  ↓
見本 / 短い説明
  ↓
撮影開始
  ↓
約 3 秒のガイド
  ↓
処理 / 保存
  ↓
完了
```

撮影中には契約に従い、姿勢や位置を少し変えるよう 2 回程度促してよい。

これは実際に距離や姿勢を測って指示するものではなく、多様なサンプルを得るためのあらかじめ用意したガイドである。

### 9.5 学習状態

バックエンドが持つ以下の状態を、ユーザー向けに自然な見せ方へ変換する。

```text
idle
preparing
capturing
processing
saving
completed
cancelled
error
```

技術用語をそのまま表示しない。

### 9.6 件数の扱い

サンプル件数を学習画面の主役にしない。

子ども向けには `3 / 5 おぼえた` のような進捗表現を優先する。

大人が必要な場合にのみ、各クラスの件数を補助情報として確認できる程度でよい。

## 10. 検証画面

検証画面は、大人が学習結果を確認するための簡易テスト画面として設計する。

ゲーム世界から完全に切り離す必要はないが、対戦・学習より情報量を増やしてよい。

基本フロー:

```text
ゆび / かお を選択
  ↓
正解ラベルを選択
  ↓
検証開始
  ↓
実際に動く
  ↓
結果表示
```

最低限表示可能な情報:

- expectedLabel
- predictedLabel
- confidence
- 判定成立 / 不成立

例:

```text
正解: 上
判定: 上
信頼度: 82%
```

confusion matrix や過去の検証セッション表示は、必要性が生じた場合に追加可能。

ただし以下は本番検証画面にも原則不要。

- Tensor 数
- TF.js backend 名
- KNN k
- 特徴量
- 毎フレーム推論ログ

検証画面は「デバッグコンソール」にはしない。

---

## 11. 設定画面

設定画面は大人向けのシンプルな管理画面とする。

ゲームらしさを無理に持ち込むより、安全性と理解しやすさを優先する。

大きく以下の領域を持つ。

### 11.1 共有データ

- 現在の共有データ ON/OFF
- ON / OFF 切替
- 切替後の再構築中表示

再構築中は推論・対戦不可であるため、その状態をアプリ全体へ正しく反映する。

### 11.2 データの出し入れ

- Local Dataset の Export
- Dataset ファイルの Import

Import エラーは契約で定義された区分に応じて、人間向けのメッセージへ変換する。

### 11.3 データ削除

以下を明確に区別する。

- この端末で学習したデータを削除
- 読み込んだデータを削除
- 完全初期化

特に完全初期化は破壊的操作として十分な確認を入れる。

子どもの通常ゲーム導線には削除操作を置かない。

---

## 12. アプリ全体の準備状態

UI は少なくとも以下を区別する。

```text
initializing
camera-unavailable
model-loading
rebuilding-classifiers
ready
error
```

重要なのは、内部実装の説明ではなく「今ゲームを操作できるか」をユーザーへ自然に伝えることである。

例:

- `initializing` / `model-loading` → 起動準備中
- `rebuilding-classifiers` → データを準備中
- `camera-unavailable` → カメラを使えないことを明示し、必要な対応を案内
- `error` → 復帰可能なら復帰操作を提示

開発者向けの内部エラー文字列をそのまま子ども向け画面へ出さない。

---

## 13. キャラクターデザインの方向性

対戦相手は初期版では 1 キャラクター固定とする。

キャラクター選択、ステージ選択、着せ替え、コレクション要素などは初期 UI の対象外。

キャラクターの方向性:

- シンプルなオリジナルマスコット
- 人間そのものではない
- ロボットそのものでもない
- 動物にも強く寄せすぎない「謎の生き物」程度
- 顔向きと手の方向が分かりやすいシルエット
- 表情の変化が読み取りやすい
- 2D イラスト調
- 色数は少なめ
- 子どもっぽすぎない

キャラクターは常時大きく動かし続けない。

静止時は落ち着き、以下の瞬間だけリアクションを強くする。

- `ほい！`
- 得点
- 判定不能
- 勝ち / 負け

## 14. ビジュアルデザイン

### 14.1 全体トーン

狙う印象:

> 親しみやすいスマホゲーム。小学生でも楽しいが、大人が見ても幼稚・ダサいとは感じにくい。

任天堂系のプロダクトから参考にするのは、キャラクターそのものや具体的な意匠ではなく、以下の考え方である。

- 主役が明確
- 選択肢が少ない
- 状態が直感的
- タップ時の反応が気持ちいい
- 説明文を読ませない
- 派手さを常時使わず、必要な瞬間に演出する

### 14.2 色

- ライト基調
- 白〜薄いアイボリー程度の明るい背景
- 暖色系をメインアクセントとする
- サブカラーは増やしすぎない
- AI ツールにありがちな紫 / 青ネオン主体にはしない

### 14.3 質感

- 2D フラット寄り
- ベタ塗りを中心にする
- 輪郭は適度に明確
- 影は薄く限定的
- ボタンには押したときの沈み込みなど、ごく軽いおもちゃ感を持たせる
- 複雑なガラス表現、光沢、ネオン、過剰なグラデーションは避ける

### 14.4 カード UI を増やしすぎない

すべてを角丸カードへ分割するダッシュボード型 UI は避ける。

カードは必要なまとまりを作るために限定的に使用する。

特に対戦画面は「カードの集合」ではなく「1 枚のゲームステージ」に見せる。

### 14.5 静と動

通常状態は比較的静かにする。

- 背景装飾を増やしすぎない
- キャラクター、スコア、必要な指示だけを見せる

以下の瞬間だけ画面を少し賑やかにする。

- `ほい！`
- 得点
- 勝敗

図形が少し飛ぶ、文字が弾む、キャラがリアクションするといった短い演出を使用してよい。

狙いは以下。

> 止まっているときはかわいくて綺麗。動くとゲームらしく楽しい。

---

## 15. 音と振動

ゲームは音なしでも完全に遊べるようにする。

視覚情報が本体であり、音はゲーム体験を気持ちよくする補助演出とする。

音と相性のよいポイント:

- `あっちむいて…`
- `ほい！`
- 得点
- 勝ち / 負け

将来的に短い SE やボイスを入れてよい。

ただし、音声を聞かなければ現在の状態や次の行動が分からない設計にはしない。

振動も同様に補助演出として扱う。

---

## 16. 端末の持ち方・置き方

特定の遊び方へ固定しない。

- 手に持って遊んでもよい
- 机などに置いて遊んでもよい
- UI 側から特定の置き方を要求しない
- `スマホを立てて置いてね` のような案内を通常導線には入れない

カメラを利用するゲームとして、どちらの遊び方でも成立する範囲を実機で確認しながら調整する。

---

## 17. 明確に避ける方向

以下は今回の UI の方向性と合わないため避ける。

- デスクトップ向け 2 カラム UI を縮めただけの構成
- カメラと CPU を 50:50 で並べるビデオ通話風レイアウト
- 対戦 / 学習 / 検証 / 設定を同格にした常時ボトムナビ
- AI 管理画面風のダッシュボード
- confidence やクラス件数の常時表示
- Tensor 数や TF.js backend 表示
- KNN / MobileNet / 特徴量などの内部用語
- カードを大量に並べる UI
- 紫 / 青ネオン主体の「AI っぽい」配色
- キラキラ、ガラス、複雑なグラデーションを常用する装飾
- 幼児教材のような過剰に子ども向けのデザイン
- 常時キャラクターや背景が動き続ける騒がしい画面
- 判定不能をゲーム上の敗北として扱うこと
- バックエンドから提供されない画角品質を UI が推測して指導すること
- じゃんけん UI

---

## 18. 現行 UI からの扱い

現行 UI は以下の特徴を持つ。

- デスクトップ寄りの 2 カラム
- カメラと認識結果を常時大きく表示
- `おしえる / ためす / たたかう` の上部タブ
- 押しっぱなし学習
- じゃんけん操作
- Tensor / backend 等の開発情報
- ダークテーマ

今回の再設計では、現行画面構造を維持しながら見た目だけ変更する方針は取らない。

UI は `ui-contract.md` を正として、ほぼ白紙から再構成する。

現行コードから再利用する価値があるものは、カメラ利用やゲーム状態に応じた描画などの技術的知見であり、既存 DOM 構造や画面レイアウトそのものではない。

## 19. 実装時に調整してよいこと

以下はこの設計書で固定せず、実装・実機確認で調整してよい。

- 正確な余白
- ボタンサイズ
- カメラ窓の具体的な寸法
- キャラクター領域の具体的な比率
- フォントサイズ
- 最終的な文言
- アニメーション時間
- イージング
- SE / 振動の具体的内容
- 対戦開始設定の具体的な UI
- 設定値の保持方法
- 各画面内の細かな情報配置
- 検証結果の詳細表示量
- 学習済み進捗の細かな見せ方

ただし、これらを調整するときも本書の大きな原則を壊さないこと。

## 20. 実装判断の優先順位

実装中に UI 上の判断に迷った場合は、次の順に優先する。

1. `ui-contract.md` に違反しない
2. 対戦ゲームとして楽しい / 分かりやすい
3. 小学校低学年でも迷わず遊べる
4. 対戦画面の主役をキャラクターに保つ
5. 技術情報をユーザーへ押し付けない
6. 通常状態は静かに、必要な瞬間だけ演出する
7. 大人が見ても幼稚に見えない
8. 実装の単純さ

「機能を全部見せる」より「今必要なものだけ見せる」を優先する。
